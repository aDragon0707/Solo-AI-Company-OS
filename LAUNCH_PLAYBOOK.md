# Launch Playbook

**Purpose:** Help maintainers publish Solo-AI-Company-OS clearly without turning it into hype or heavy software too early.

---

## Launch Positioning

Use this pain-first line:

```text
Stop losing your AI company inside chat history.
```

Then explain the project in one sentence:

```text
A disciplined Markdown operating system for solo founders managing AI employees.
```

The project should be framed as a practical operating system, not a prompt pack.

---

## Who To Reach First

Start with people who already feel the pain:

- solo founders using AI every day
- indie hackers shipping with AI help
- Obsidian users who manage projects in Markdown
- consultants who run many AI chats across client work
- non-technical founders trying to understand technical projects

Avoid broad messaging like "for everyone using AI." The first audience should be narrow enough to recognize itself instantly.

---

## Public Launch Assets

Before a loud launch, prepare:

- README with clear first screen
- system map image
- `EXAMPLE_DAY_1.md`
- license
- contribution rules
- one short launch post
- three screenshots or image previews

The first public version should show the workflow, not only the folder tree.

---

## Launch Post Shape

Use this structure:

1. Problem: AI work disappears into chat history.
2. Cost: decisions, handoffs, and project truth get blurred.
3. Solution: a Markdown-first company memory system.
4. Demo: show Founder Decision Log, AI roles, and worklog handoff.
5. Boundary: V1 requires no server, database, or paid tool.
6. Invitation: fork it, adapt it, and share what breaks.

Short version:

```text
I built an open-source Markdown OS for solo founders managing AI employees.

It turns scattered AI chats into founder decisions, role prompts, worklogs, handoffs, and a learning loop.

The core rule: AI can execute and challenge, but founder decisions remain the source of truth.
```

---

## Suggested Channels

Use channels where people already discuss AI work systems:

- GitHub
- X
- Hacker News Show HN
- Reddit communities for Obsidian, indie builders, and AI workflows
- Indie Hackers
- Product Hunt after the README and examples feel polished

Start with quieter channels first. Use the first reactions to fix confusing wording before a wider launch.

Show HN is a fit only after the public repo is easy to try. Do not submit a pure landing page or fundraiser.

Product Hunt is better after you have visuals, a crisp tagline, and a clear maker story.

---

## Charging Recommendation

Keep the core repo free and open-source.

The paid path should be self-serve, not founder-dependent consulting.

Recommended model:

| Layer | Price Strategy | Reason |
|---|---|---|
| Free Core | free | builds trust, adoption, and public proof |
| Pro Template Pack | paid | gives buyers a more complete ready-to-use package |
| Automated setup tools | paid or bundled with Pro | saves setup time without requiring live help |
| Role packs | paid | serves specific founder types without custom work |
| Pack updates | paid upgrade or included updates | keeps the product improving over time |
| GitHub Sponsors | optional later | supports maintenance after users already value the repo |

The free repo should remain complete enough to use. The Pro Pack should save time and add depth, not unlock the basic system.

Good paid assets later:

- one-click vault generator
- richer AI employee role packs
- founder, consultant, creator, and agency variants
- Day 1, Day 7, and Day 30 operating flows
- larger fictional example vaults
- packaged release ZIP files
- short setup videos or written setup guides

Avoid making the business depend on:

- manual setup calls
- custom vault cleanup
- ongoing private support
- promises to fix each user's workflow by hand

If private help is offered at all, it should be rare, expensive, and clearly outside the normal product. The default buyer experience should be self-serve.

---

## Contribution Boundary

The project should accept improvements that make the core clearer.

Accept:

- better examples
- clearer role prompts
- onboarding improvements
- safer handoff formats
- spelling and link fixes
- small navigation improvements

Be careful with:

- new top-level folders
- heavy automation
- tool-specific workflows
- large rewrites of system principles
- features that require a server or paid account

Reject:

- real private company data
- vague AI hype
- prompts that let AI guess missing facts
- changes that weaken founder decision authority
- changes that make V1 depend on V2

---

## First Success Metric

The first success metric is not stars.

The first success metric is:

```text
Can a new founder set this up in 15 minutes and understand what to do next?
```

If yes, then stars, forks, posts, paid services, and V2 can follow.
