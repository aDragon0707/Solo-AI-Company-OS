# Product Boundary

**Purpose:** Define what belongs in the free open-source Core, what can become a future Pro Pack, and what must never be hidden behind paid access.

---

## Product Model

Solo-AI-Company-OS should be a self-serve product.

The public repo earns trust by being useful on its own. Paid products should save time, add depth, and package specialized variants without making the Core incomplete.

```text
Free Core = usable operating system
Pro Pack = faster setup, richer examples, deeper variants
```

---

## Free Core Includes

The free repo should keep:

- stable folder structure
- `OBSIDIAN_HOME.md`
- founder thinking, decision, and retrospective ledgers
- company state dashboard
- AI-01 to AI-05 base roles and start prompts
- coordination protocol
- AI text maintenance protocol
- worklog index and worklog template
- learning lab
- claim boundary principles
- minimal handoff prompt
- at least one fictional first-day example
- license and contribution rules
- a basic self-serve initialization path
- basic release validation and packaging scripts

The Core must remain usable without payment, a server, a database, or a paid tool.

---

## Future Pro Pack May Include

A future paid pack may include:

- richer vault generator options
- packaged ZIP releases
- additional fictional example vaults
- Day 1, Day 7, and Day 30 operating flows
- role packs for founder types
- advanced AI employee prompts
- more detailed review checklists
- short setup guides or videos
- convenience scripts for packaging and validation

These assets should make adoption faster. They should not be required to understand or run the basic OS.

---

## Never Lock Behind Pro

Do not make these paid-only:

- founder decision log
- worklog template
- AI-01 coordination role
- basic AI employee model
- company state dashboard
- system principles
- claim boundary rules
- handoff discipline
- basic initialization path
- core README and onboarding

If a user cannot run the basic OS from the free repo, the boundary has failed.

---

## No Private Data In Public Or Pro

Do not include:

- real customer names
- private company notes
- private founder reflections
- proprietary project details
- internal sales material from a real business
- sensitive technical implementation notes from another repo
- examples that can identify a real client, product, or engagement

All examples must be fictional.

If a sample is inspired by real work, rewrite it until it is no longer traceable to the original source.

---

## Maintenance Rule

When adding a feature, ask:

```text
Does this make the free Core clearer and more useful?
Or does it belong in a future Pro convenience layer?
```

Core improvements should reduce confusion.

Pro improvements should reduce setup time or add specialized depth.
